## 1. What was learned (ranked by reputability)

### 1.1 A skill the agent never invokes is a net negative (Vercel, official org)
- Source: vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals (Jan 2026), surfaced independently
  this week via agent-sh/agnix which cites it as the "skills invoke at 0% without correct syntax" case.
- Skills were **not invoked in 56%** of eval cases → **+0pp** over the no-docs baseline (53% → 53%), and the
  unused skill made some metrics *worse* (58% vs 63% on tests). With an explicit "invoke the skill" line in
  AGENTS.md: 79%. A compressed 8KB docs index **always resident** in AGENTS.md: **100%**.
- Instruction wording is fragile: "You MUST invoke the skill" makes the agent anchor on docs and miss project
  context; "explore the project first, then invoke the skill" scored better on the same material.
- **Consequence for ATLAS:** the rules that must hold every single time — pin the interpreter for cron scripts,
  run the injection-gate sweep, sudo via `sudox`, the submission order — should not depend on a skill triggering.
  They belong in an always-resident context file, with the skills holding procedure.

### 1.2 Semantic supply-chain attacks on skill registries (arxiv 2605.11418, May 2026)
- SKILL.md is **operational text**: description-only framing flips selection between two functionally identical
  skills in **77.6%** of paired trials; short textual triggers shift embedding retrieval (86% pairwise win,
  80% Top-10 placement); semantic evasion avoids a blocking verdict in 36.5–100% of cases.
- Our descriptions are therefore both the routing contract and an attack surface — audit the framing, not only
  the keywords.

### 1.3 SkillSentry — dynamic testing, and why "clean scan" means unmeasured (arxiv 2608.03485)
- Honey-world framework: infer the skill's intended capability boundary, build an LLM-simulated environment with
  decoy resources, adaptively generate tasks, then compare skill-enabled vs **matched no-skill** executions and
  ground each suspicion in code + verified traces. 99.50% recall; **92.95% F1 under semantics-preserving
  evasion vs 80.07%** for the strongest static/LLM baseline.
- Conditional behaviour (state-, resource-, history-dependent) is invisible to static scanners *and* to LLM reads.
  For high-privilege or third-party skills the only real question is: *what does it do here that the same task
  without the skill does not?*

### 1.4 Who Maintains Agent Skills (arxiv 2609.05677, Sep 2026)
- Divespace: 5 public skill repos, 873 commits, 143 skill files, 254 substantive post-creation edits
  (Oct 2025–Jun 2026). **100%** of substantive edits went through a named human account; 62% carried an AI
  co-author trailer; operations are dominated by additions and corrections.
- Validates the shape of this very sweep (AI drafts → human merges) and releases codebooks + a replay protocol
  for automated curators.

### 1.5 Registry-grade audit methodology (Skillstore Security Center, Jul 2026)
- Separate trust signals, none substituting for another: public ≠ safe, audited ≠ safe, signed manifest ≠
  harmless. Publish **capability context** and **confirmed concern** as different fields, and bind every verdict
  to repo / content / tree / audit-payload identity.
- Adopted into our triage: a finding is a *concern* only when the capability is undeclared or the composition is
  wrong; otherwise it is context to report separately.

### 1.6 Optional second linter: agnix (agent-sh/agnix)
- 457 rules across Claude Code / Codex / OpenCode / Cursor / Copilot configs; `uvx agnix <root>`, no install.
- On this library: 203 errors / 400 warnings, but **134 of the errors are one rule** —
  `metadata must be a map from string keys to string values` (our nested `metadata.hermes`; a *portability*
  finding for anything re-exported, not a Hermes defect) — and ~26 more are our own bug-bounty handles parsed as
  `@import` targets. Real signal: hard-coded `/home/pro-g` paths (9 files). Verdict: reporting aid, not a gate.

## 2. What was implemented and why

`~/.hermes/venvs/skillsec` was **orphaned**: `/usr/bin/python3` moved 3.12.3 → 3.14.4, the venv's
`bin/python3 -> /usr/bin/python3` followed it, while every package sat in `lib/python3.12/site-packages`. Result:

cannot start, which looks exactly like a scanner that found nothing.
- Rebuilt on a **uv-managed pinned interpreter** (`uv python install 3.12`; `uv venv --python 3.12`), installed

- **Split into one venv per scanner** — co-installing is now genuinely unsatisfiable: SkillSpector 2.9.6 wants

  `skill-scanner==0.3.3` pins `typer==0.25.1`. Two-line `sh` exec shims in `skillsec/bin` keep every documented
  path valid, so `skill_second_opinion.py` needed no change.
