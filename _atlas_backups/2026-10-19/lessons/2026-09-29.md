## 1. What was learned (ranked by reputability)

### 1.1 OWASP Agentic Skills Top 10 (AST10) — the missing security axis
- Source: https://owasp.org/www-project-agentic-skills-top-10/ (April 2026). Reputability: **standards body**; steering includes AWS, Google, Anthropic, NIST, Gartner, JP Morgan, Harvard; peer-reviewed by 100+ practitioners. Also surfaced independently by Tencent Zhuque Lab's TSRC write-up.
- The 26-smell taxonomy (arxiv 2607.01456) answers "does this skill work / route correctly".
  AST10 answers "can this skill or its distribution path hurt the host". We only had the first.
- Ten risks across five lifecycle phases:
  - Author & Publish — AST04 Insecure Metadata
  - Distribute & Install — AST02 Supply Chain Compromise
  - Load & Permission — AST01 Malicious Skills, AST07 Update Drift
  - Execute & Isolate — AST05 Untrusted External Instructions, AST03 Over-Privileged, AST06 Weak Isolation
  - Detect & Govern — AST08 Poor Scanning, AST09 No Governance, AST10 Cross-Platform Reuse
- **This framework had been published for five months without appearing in any prior sweep.** Both the
  Brave "agent skills" queries and the arxiv crawl missed it; it was found only via a Chinese-language
  regional query. Lesson: the English-language discovery net has a blind spot for non-paper frameworks.

### 1.2 Composition attacks defeat scanners — "zero findings" is not a clean bill of health
- **SkillDRE** (arxiv 2609.32400, Sep 26): dual-stage red-team evolution of complete malicious skill
  packages against four victim models. **45.28% average attack success rate, and the final submitted
  skills received zero scanner findings** while largely preserving benign-task performance.
- **Tencent Zhuque Lab** (TSRC, Apr 2026; scanned 50,000+ ClawHub skills with A.I.G): their showcase
  sample **passed ClawHub's entire detection stack** — regex code scanning, five injection-pattern
  detectors in SKILL.md, an LLM five-dimension safety evaluation, and VirusTotal — because every step
  was individually reasonable and *honestly documented*: a remote fetch, a multi-layer transport
  decoder presented as a binary-safe encoding requirement, and a deserialization call. The C2 decided
  the instruction order at runtime with a decode header. **The composition was the attack; no single
  step is a marker.** Reputability: top-tier vendor security lab.
- This is exactly **AST08 "Poor Scanning"**: natural-language-plus-code blends defeat signature
  scanners. Our previous triage rule keyed on *undocumented* capabilities and verbatim override
  strings — the new generation documents everything and composes harmless steps into an RCE chain.

### 1.3 Popularity is not a trust signal — the "popularity-security paradox"
- **SkillProbe** (Shanghai Jiao Tong, arxiv 2603.21019; 2,500 ClawHub skills): **>90% of high-download
  skills failed strict security audit**; download count does not predict safety, and high-risk skills
  cluster into one giant connected component (cascade risk is systemic).
- **Snyk ToxicSkills** (3,984 skills across OpenClaw, Claude Code, Cursor, VS Code): 280+ samples
  leaked credentials directly; every platform had substantial defects.
- **Silverfort**: ClawHub's ranking could be inflated by an unauthenticated request. Their PoC pushed
  a malicious skill (disguised as an Outlook integration, embedded exfil payload) to **rank #1** — and
  because agents preferentially install high-ranked skills when picking tools autonomously, ranking
  manipulation equals automated mass poisoning.
- Supply side: 74.6% of 50,000 skills (27,818) declare network permission; file-read + network-egress
  is a complete exfil path. 15,427 developers, but the top 20 accounts published 12.9% of the corpus,
  and one account shipped 955 skills in 90 days (~10.6/day) with naming-linked sibling accounts.
- **This directly corrected our own discovery methodology**, which ranked "1000+★ community repo" as
  a validation tier.

### 1.4 Selective skill activation now has a mechanism (and it matches what we already do)
- **SkillDelta** (arxiv 2609.32274): paired executions of the same agent with and without a skill
  predict whether the skill will help *before* the agent acts. +4.3% success over random activation —
  and **most of the gain comes from allocation across task groups, not within-group selection**.
  Code: github.com/TankTechnology/skilldelta.
- **Progressive disclosure** (arxiv 2609.35692, Workday, Sep 28): lazy-loading skills **improves
  retrieval quality but marginally degrades latency** — i.e. our `references/` split is a quality
  trade, not a speed win. Worth knowing before optimising for latency.
- **M-SQE** (arxiv 2609.18445): the ecosystem is English-centric — an audit found **zero in-language
  skill content for Swahili and Hindi**, so retrieval returns a related-but-unusable candidate and
  accuracy collapses. M-SQE lifts Hindi +12.9pp / Swahili +5.6pp.
- **HEXIS** (2609.30123) / **SkillFocus** (2609.34397): compile skills into extended FSMs to separate
  knowledge from control flow (+16.2pp over Skill+ReAct, 38-89% fewer tokens); evolve a skill against
  a fixed *capability space* rather than its current text (−24% evolution tokens, +5.7pp).

## 2. What was implemented and why

### 2.1 FIXED — silent total pipeline outage (highest-value fix of the run)
A Hermes-bundled interpreter (`~/.hermes/tools/python-3.14.7*/bin/python3`) is now first on PATH and
**does not include PyYAML**. Result: the bridge refused to run ("PyYAML required") and the validator
reported `PyYAML not installed` for **all 225 skills** — a total, silent outage of the mandatory
pipeline that presents itself as a data problem.
- Fix 1: installed `pyyaml` into that interpreter (794 kB wheel).
- Fix 2 (durable): added `ensure_yaml()` to both `skill_validator.py` and `opencode_skills_bridge.py`
  — re-execs via `os.execve` under a known-good interpreter (`/usr/bin/python3`, 3.12, 3.13), guarded
  by an `_ATLAS_YAML_REEXEC` env flag so it can never loop.
- **Verified by negative test**: ran the validator under a purpose-built PyYAML-free venv
  (`/usr/bin/python3 -m venv --without-pip /tmp/noyaml`). It re-exec'd and returned the real audit
  (225 skills, 2 errors) instead of 225 bogus errors.

### 2.2 ADDED — OWASP AST10 security axis in `skill-quality-audit`
- New `references/owasp-agentic-skills-top10.md`: lifecycle map, all ten risks with severity, Tier-0
  checks (always) vs Tier-1 checks (community/unknown-provenance or high-privilege only — deliberately
  tiered to avoid the excessive-procedure smell), the composition-check procedure, and the
  popularity-is-not-trust evidence.
- New **Step 3b** in SKILL.md wiring it in, with the three corrections to older triage instinct
  (composition > markers; popularity ≠ trust; a port is an attack surface).
- Cron injection gate re-verified CLEAN after the edit (58k chars across 5 files) — mandatory per the
  standing lesson.

### 2.3 HARDENED — `opencode_skills_bridge.py` against AST02/AST07/AST10
The bridge was itself an instance of **AST10 Cross-Platform Reuse**: it rewrote frontmatter down to
OpenCode's five recognised fields and, although it stamped `atlas-source`, it **dropped the source's
`metadata.hermes` block** (tags, category, related_skills) on write.
- Now stamps provenance: `atlas-source`, `atlas-source-sha256` (source content hash), `atlas-synced`.
- Now **preserves** `metadata.hermes` (serialised with `yaml.safe_dump`, so nested keys stay valid).
- New read-only `--check` mode: reports drift between each Hermes source and its OpenCode copy,
  ignoring the timestamp line. Always exits 0 (a reporter, never a gate).
- Verified: 21/21 in sync, drift 0, missing 0.

### 2.5 METHODOLOGY — corrected methodology + worldwide net widened

installs), `rm -rf /` in 6 Trail-of-Bits skills (security tooling discussing destructive commands).
