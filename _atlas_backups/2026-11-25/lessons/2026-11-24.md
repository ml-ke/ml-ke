## 1. What was learned (with source + reputability)

**R1 — `hermes curator restore` does not clear `last_activity`, so a restored skill is re-archived on
the next pass.** Reputability: *primary evidence, own machine + official docs.*
`hermes curator ledger` records a `restore` on 2026-11-17 (last sweep) and `curator archive` on
2026-11-22 (automatic run). `hermes curator usage` at the time: 268 lifetime activity,
`last_activity` 82d. The docs page `user-guide/features/curator` states that pinned skills — **and
every skill referenced by any cron job, including paused ones** — are "skipped entirely … treated
like pin for auto-transitions", and that never-used skills get a grace floor while old-used ones do
not. Fix: restore **and** `hermes curator pin`.

**R2 — the cross-skill pointer class was invisible to the collection audit.**
Reputability: *primary evidence.* 5 live skills point into that archived skill
(`rapyd-bug-bounty` and `api-hacking-methodology` by exact reference file, `recon-to-exploitation`,
`vercel-oss-bug-bounty`, `skill-corpus-cartography` by name). `skill_reference_check.py` reported
0 findings because its regex only matched pointers *starting* with `references/|scripts/|templates/`.
This is the same seam SkillSeam measures (dangling anchor: +64% tokens, −3.1pp accuracy,
arxiv 2609.13321) — the audit prescribed it, the tool did not implement it.

**R3 — ACES (arxiv 2608.20614, NVIDIA; repo `NVIDIA/SkillEvaluator`, 4,477★ official org):
static scanning and skill value are nearly independent.**
*Reputability: arxiv + official-org repo.* On 145 real skills, scan-only gates vs LLM-judge quality
score **Spearman ρ = 0.14**; on 947 scored paired cases (with vs without the skill, same model /
sandbox / scorer) mean **Skill Lift 0.2134** (95% CI [0.1967, 0.2301]) and lift is **positive in
only 72.8%** of cases. Roughly one skill in four gives zero or negative lift under a real harness.

**R4 — Skill-Composer (arxiv 2611.30715, Chen/Li/Chen/Jin): acquisition is set selection, not ranking.**
Marketplace interfaces return single skills ordered by relevance/popularity; the highest-ranked are
often functionally redundant while required capabilities stay uncovered. Reframe: decompose the
requirement into atomic points, merge candidates across marketplaces, progressively discard overlaps,
**and report the gaps**.

**R5 — NVIDIA/SkillEvaluator is the behavioral-eval harness Step 5 has prescribed but never had.**
Tier 1 = keyless static (500+ rules, YARA, harness compatibility, PII, self-modification); Tier 2 =
semantic dedup (needs an embedding provider); Tier 3 = live with/without evaluation (needs an LLM
provider). Live-verified: `skillevaluator tier1 <skill-dir>` works keyless and exits 1 on failure;
`tier2`/`tier3` exit with `No provider is configured` when `SKILL_EVAL_EMBEDDING_PROVIDER` /
`SKILL_EVAL_LLM_PROVIDER` are unset.

## 5. Hermes docs studied + operating improvement

Studied **`features/curator`** (plus the docs index for what exists). Three concrete operating facts
adopted:

1. **Pin is an operational control, not a bookmark** — pinned and cron-referenced skills are skipped
   by auto-transitions. Adopted as the durable counterpart to "restore the archived skill".
2. **`hermes curator run --dry-run`** produces the review report without mutating the library —
   the right first step before any library-wide change (recorded in the new reference).
3. **The curator is triggered by an inactivity check, not cron** (interval 7d, min idle 2h), and
   consolidation is off — which is why the only mutations we see are staleness transitions.

No config change was made: `curator.consolidate` stays off (the LLM pass costs 50-100 API calls and
we prune by hand), `curator.prune_builtins` stays off.
